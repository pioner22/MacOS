# BigSurVPN 2.0.2 — исправление ошибки route=0 и повторная проверка

## Запуск

```bash
curl -fL https://raw.githubusercontent.com/pioner22/MacOS/main/vpn.sh | bash
```

В начале должна появиться версия **2.0.2**. Дополнительный VPN-ключ не требуется. Возможен только запрос пароля администратора macOS. Профиль и ссылка подписки не менялись. Homebrew не нужен.

## Ошибка на фотографии

У пользователя загрузка runtime и профиля прошла проверку SHA-256. После получения прав администратора версия 2.0.1 завершилась на предварительной проверке:

```text
Не удалось проверить маршрут 2606:4700:4700::1111 (route=0).
```

До загрузки ядра и попытки подключения к VPN-серверу эта попытка не дошла. Фотография не содержит исходные stdout/stderr самой команды route, поэтому точный ответ ядра на этом Mac не получен.

В исходниках Apple обнаружен механизм, воспроизводящий показанный результат: при RTM_GET функция print_getmsg() печатает ошибку rtm_errno и возвращается без имени интерфейса, а вызывающая rtmsg() затем возвращает 0. В версии 2.0.1 известное сообщение об отсутствии маршрута распознавалось только при коде 1. В сети без внешнего IPv6 это могло блокировать установку, хотя доступ по IPv4 был исправен.

Первичный источник: `apple-oss-distributions/network_cmds`, commit `97e27e6244c16d399bfeb254315ddc5828711c56`, файл `route.tproj/route.c`, функции `rtmsg()` и `print_getmsg()`.

## Изменения

| Область | Исправление |
|---|---|
| Разбор route | Явные известные сообщения об отсутствии/недостижимости маршрута распознаются при коде 0 и 1. Пустой вывод, тайм-аут, ошибка прав, неоднозначность и неизвестная диагностика остаются ошибками. |
| Проверка до/после VPN | Отсутствующий исходный IPv6-маршрут не препятствует установке по IPv4. После подключения маршруты IPv4 и IPv6 по-прежнему обязаны проходить через TUN. При отключении отсутствие исходного IPv6 больше не считается неудачным откатом. |
| Диагностика route | При неизвестном результате сохраняются ограниченные stdout/stderr, код и команда в `private/route-diagnostic.json`; краткий вывод показывается в сообщении. Сам файл имеет права 0600. |
| Ошибки запуска | Сообщения супервизора через stdout раньше уходили в /dev/null. Теперь оба потока направлены в ограниченный startup.log. Подробное логирование каждого соединения остаётся выключенным. |
| Готовность службы | Окно ожидания контроллера увеличено с 20 до 30 секунд, чтобы не быть короче 25-секундного ожидания супервизора. Если готовность не наступила, выводится явная ошибка и вызывается откат, а не продолжается общая проверка DNS. Отдельные системные команды имеют собственные тайм-ауты. |
| Порядок остановки | Сначала завершается и ожидается дочернее ядро, затем освобождается временная DNS-сессия. Освобождение DNS всё равно предпринимается при исключении во время остановки ядра. |
| Недействующий маршрут | Флаги REJECT/BLACKHOLE не принимаются за исправный маршрут VPN только потому, что в выводе есть интерфейс. |

Не отключаются IPv6, проверка сертификатов, SIP или Gatekeeper. Проверки после запуска не ослаблены до одного лишь наличия процесса или изменения IP.

## Фактически выполненная проверка

В этом проходе выполнены **53 целевых регрессионных теста**, все прошли на **Linux, Python 3.13.5**:

```text
Ran 53 tests in 0.357s
OK
```

Проверены варианты вывода route, продолжение предварительной проверки без внешнего IPv6, строгий отказ при отсутствии IPv6-маршрутов после запуска, остановка, ошибки ожидания службы, журналирование и порядок очистки DNS. Системные вызовы macOS, маршруты, DNS и VPN в этих тестах подменены. Реально выполнялись разбор данных, файловые операции, Bash syntax check, передача stdin и ограничение времени отдельных локальных дочерних процессов.

Дополнительно прошли `bash -n vpn.sh`, компиляция Python-файлов и сверка контрольной суммы runtime с pin загрузчика. Git blob SHA опубликованных runtime, загрузчика и нового тестового файла совпали с локальными проверенными файлами.

Один и тот же смоделированный ответ Apple RTM_GET сравнен на точных исходниках старой и новой версии:

```text
returncode: 0
stdout: route to: 2606:4700:4700::1111
stderr: route: message indicates error 3: No such process

2.0.1: ошибка «Не удалось проверить маршрут ... (route=0)»
2.0.2: NO_ROUTE — подтверждённое отсутствие маршрута
```

Это воспроизведение по исходникам Apple, а не извлечённый с фотографии stderr пользователя. При другом неизвестном выводе новая версия сохранит его для следующей диагностики.

Прежние 129 тестов из предыдущего аудита в этом проходе целиком не перезапускались; они не прибавлены к результату 53/53. Проверка всей цепочки на реальном Big Sur, настоящая регистрация DNS, связь с провайдером и реальная скорость здесь не выполнены. Локальные тесты не являются подтверждением отсутствия любых ошибок.

Команды разработчика:

```bash
python3 -m unittest -v test_vpn_routes
python3 -m py_compile vpn-runtime.py test_vpn_routes.py
bash -n vpn.sh
```
