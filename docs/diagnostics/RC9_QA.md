Дата: 2026-09-21. Кандидат 2.0.0-rc9; bootstrap 1.4; реестр 2026-09-20.1.

## Вывод

Доступные программные проверки проходят после пяти исправлений. Утверждение «все аппаратные тесты работают в настоящей Recovery» пока не подтверждено. Этот аудит выполнялся на Linux, без доступа к Mac и без испытаний устройства пользователя.

Исходный main: `e148d63c02dcbb9f9fdaf2366ae5245e26258802`, rc8, payload `14656dffb0644c417b72abe2d6bb090c56f70cc2`. Исторические результаты rc7/rc8 не включены в число новых проверок. Этот документ описывает кандидат; наличие ветки или PR не означает переключения main.

Это не изоляция произвольного враждебного процесса, самостоятельно создающего другую сессию, и не гарантия завершения процесса, заблокированного в ядре. GNU Bash 3.2 собран локально из официального архива `https://ftp.gnu.org/gnu/bash/bash-3.2.tar.gz`, SHA-256 `26c99025b59e30779300b68adb764f824974d267a4d7cc1b347d14a2393f9fb4`. Старый shell использован только как инструмент проверки, не включён в продукт. Попытка собрать 3.2.57 не завершилась из-за отсутствия yacc; её результат не заявляется проверенным.

Проверки Bash 3.2 запускают выбранный shell непосредственно; BASH_VERSION не подменяется. Вложенные обращения к системному /bin/bash на Linux по-прежнему используют системный Bash 5.2. Это не полный прогон всего комплекса в Apple Bash/Recovery.

```bash
python3 tools/build_diagnostics_registry.py --check
python3 -m unittest discover -s tests/diagnostics_v2 -v
MACDIAG_TEST_BASH=/absolute/path/to/bash-3.2/bash \
  python3 -m unittest discover -s tests/diagnostics_v2 -p test_rc9_audit.py -v
```

В macOS workflow добавлен запуск новых регрессий с /bin/bash, без аппаратной нагрузки; восстановление Actions остаётся отдельной задачей. Изменение workflow само по себе не является его успешным исполнением. Защиты репозитория не отключались.

## Внешние зависимости и следующий этап

1. Восстановить запуск GitHub Actions, затем выполнить существующие Intel/Apple-silicon macOS задачи. Проверенный main-run `35565824809` ранее завершился до runner; зелёный CI этим аудитом не заявлен.
2. Опубликовать и проверить `diagnostic-fixtures-v1`. На момент аудита GitHub Release API возвращает 404. Последний найденный workflow эталонов `35139376608` завершился failure, шаги отсутствуют. Генератор/manifest существуют; нормальный полный сценарий требует 1429 МиБ передач, включая повторы и 16-МиБ Range. Этот трафик не выполнялся.
3. Получить реальные паспорта Recovery без установленной ОС и full macOS. Проверить точные версии Bash, Perl, curl и возможности системных утилит. Runtime-пробы не заменяют этот этап.
4. Собрать, проверить и поставлять совместимые native-бинарники для Recovery с обязательным mlock и честным покрытием. Только затем планировать отдельную валидацию большого объёма RAM/bridge и Metal на настоящем Mac.

Fallback метаданные PowerShell v7.6.6 сверены с Release API: `PowerShell-7.6.6-win-fxdependent.zip` — 23012318 bytes, SHA-256 `ea3c73ac3bf7afa07432c65b8d9f16b8945befa216cec38a51b6e213dc8fa709`; `powershell-7.6.6-osx-x64.pkg` — 75026625 bytes, SHA-256 `68fd85010f02e5e16634f811da8d72a5ee58e01c24b353df5bf4acd3a645f56e`. Это проверка метаданных, не новый полный прогон скачивания. Fallback не заменяет штатные эталоны и Range, итог ограниченного сценария остаётся INCONCLUSIVE.

Неподтверждёнными остаются чувствительность к настоящим дефектам железа, внезапное отключение питания и поведение системных вызовов на повреждённом устройстве. Сетевая недоступность, ошибка сборки, отсутствие инструмента или ресурса не считаются доказательством дефекта оборудования.
