# Приёмка после ремонта — 2.0.0-rc1

## Назначение

Новая версия предназначена для независимой проверки после ремонта Intel Mac, прежде всего A2141. Это кандидат версии с выполненными программными регрессиями, **не сертифицированный сервисный прибор**. Она не подтверждает заранее ни качество ремонта, ни неисправность конкретной микросхемы. Реального Mac/Recovery/GPU в локальной среде разработки не было.

## Запуск

Постоянный вход остаётся `st.sh`. Пункт **16 — POST-REPAIR** запускает комплекс без стирания разделов. Пункт 17 — отдельная проверка нового временного файла; пункт 18 — отдельный 40-ГиБ RAM→внешний RESCUE тест с дополнительным согласием. Старые номера 2/3/4 соответствуют новой нативной RAM Quick/Full/Map. Профиль модели и загруженной ОС доступен в пункте 15.

Перед запуском: подтверждённая резервная копия, питание, исправное охлаждение, закрытые лишние приложения, полная macOS и установленные Command Line Tools. Нативные RAM/файловый/Metal тесты сейчас ограничены полной Intel macOS. Recovery, отсутствие компилятора, отказ mlock или неизвестная среда дают INCONCLUSIVE, а не аппаратный FAIL. Автоматической установки инструментов, sudo, смены настроек безопасности и ремонта файловой системы нет. mlock может потребовать повышенных прав; программа сама их не получает.

Без сети можно перенести весь `diagnostics_v2/` с manifest.tsv и запустить `bash diagnostics_v2/run.sh menu`. Сетевые тесты всё равно требуют сети. Для такой локальной копии в отчёте будет LOCAL_UNPINNED, если она запущена не проверяющим загрузчиком.

## Что исправлено

- Каждая загрузка имеет локальные переменные, собственный каталог, новый счётчик байтов и процесс SHA-256. Повтор не меняет URL/эталон соседнего вызова.
- В потоковом curl нет внутренних retries. После оборванной попытки новая передача начинается с новым хэшером. Восстановившаяся передача остаётся INCONCLUSIVE/RECOVERED_TRANSFER_NOT_CLEAN, а не чистым PASS.
- Проверяются успешность всех частей конвейера, точный размер, SHA-256 и последний HTTP-ответ. Для Range нужны 206 и точный Content-Range с полным размером объекта. Возврат всего объекта вместо Range — ограничение протокола, не диагноз DRAM. Range-тест не является полным тестом возобновления файла через `curl -C`.
- RAM и RAM→диск — отдельные тесты. В bridge успешная проверка источника не скрывает ошибку чтения файла. Программная регрессия искусственно портит файл после правильной записи и получает FAIL при чистых RAM pre/post-проверках.
- RAM engine на C использует отдельное фиксированное mmap-выделение с защитными страницами, volatile-чтения/запись и mlock. Full — 134 шаблона, включая 64 walking ones и 64 walking zeros. Отказ закрепления останавливает тест до стресс-цикла; OOM, сигнал и тайм-аут не превращаются в диагноз DRAM.
- В GPU используется уникальный бинарный файл только после успешной текущей компиляции. Проверяются объекты/энкодеры и завершение command buffer. Тест экспериментальный: 256 МиБ private-буферов на доступное устройство, восемь шаблонов. Это не проверка всей VRAM и не локализация отдельного чипа. Metal здесь не исполнялся.
- Статус этапа передаётся отдельным TSV-контрактом. Exit 0 без соответствующего завершённого результата не считается PASS. FAIL не маскируется последующим пропуском или ручным этапом.
- Логи создаются до нагрузки, пишутся во время теста; supervisor ограничивает время и завершает дочерние процессы. Промежуточные sync снижают риск потери хвоста, но **не гарантируют сохранность при внезапном отключении**.
- Весь пакет загружается с одной закреплённой Git-ревизии, с проверкой размера и SHA-256 каждого файла и manifest. Это контроль целостности относительно доверенного загрузчика, не цифровая подпись.

## Накопитель: только новый файл

Пункты 1 и 13 и прямой `ssd_test.sh` **заблокированы** до отдельного аудита старого RAW-движка. Старые mhdd_v2.part* сохранены для анализа; не собирайте и не запускайте их вручную. В предыдущем коде были глобальные переменные, объединённые состояния и автоматические разрушительные ветви. Исправления сетевого кода нельзя автоматически считать аудитом этих ветвей.

Файловый тест создаёт уникальный O_EXCL-файл внутри подтверждённого каталога, никогда не открывает сырой накопитель и не перезаписывает существующие пользовательские файлы. По умолчанию 1 ГиБ, два цикла записи, по два чтения каждого результата. Проверяется каждое 64-битное слово. F_NOCACHE и F_FULLFSYNC на macOS запрашиваются и проверяются; их недоступность даёт INCONCLUSIVE. Они не доказывают конкретное физическое размещение NAND и не заменяют проверку после отключения питания. При FAIL остаётся только собственный тестовый файл для анализа; при успехе/отмене он удаляется. В начале оставляется запас свободного места; одновременная запись другими приложениями может его изменить.

Bridge удерживает и закрепляет 40 ГиБ источника, требует не менее 64 ГиБ установленной RAM, внешнего RESCUE, свободного места и дополнительного согласия RAM-BRIDGE. Он не включён автоматически в RAM Full или приёмку. Любое несовпадение здесь относится к общему RAM/CPU/драйвер/кабель/накопитель пути, пока независимая диагностика не локализует причину.

## Итог приёмки

Порядок пункта 16: self-test комплекта → сведения и питание → RAM Quick → RAM Full → CPU → GPU → HTTPS → скачивание → отдельный временный файл → ручная/независимая часть. При RAM/CPU FAIL или неполном результате зависимые тесты не запускаются. GPU FAIL также останавливает последующую нагрузку.

PASS отдельных стадий не превращается в сертификат машины. Даже при чистых автоматических стадиях общий результат будет **PENDING_MANUAL**, пока не выполнены независимая проверка памяти, повтор после полного выключения, Apple Diagnostics, сон/пробуждение, экран, батарея/зарядка, Wi-Fi/порты и сверка акта ремонта. Это не автоматически отслеживаемый многозагрузочный протокол: логи сеансов нужно сравнить отдельно. Не заявлены автоматический 8–12-часовой burn-in, тест всех физических ячеек, GPU switching, ECC-счётчики и гарантированное восстановление после kernel/driver hang.

## Сетевые эталоны

Свой Release diagnostic-fixtures-v1 при последней проверке не был опубликован. Размеры 1/8/32/128/512 МиБ и 16-МиБ Range пересчитаны независимо. Скрипт не выдаёт полный PASS, когда собственные файлы/Range недоступны: он выполняет ограниченные резервные загрузки и оставляет INCONCLUSIVE. Код может проверить GitHub-путь; три HTTPS endpoint не являются доказательством скачивания установщика Apple или счётчиком физических разрывов Wi-Fi.

## Достоверность старых выводов

Старые Perl-логи — наблюдения несовпадений, а не самостоятельная локализация DRAM/BGA/IMC. Виртуальные offset/chunk между выделениями и перезагрузками нельзя считать одним физическим адресом. Замена движка на C нужна для независимого сопоставления, а не для утверждения, что прежние результаты доказанно ложны или что все прежние сбои были аппаратными.

## Что реально проверено

Локальные регрессии: Linux, Bash 5.2, Python unittest, настоящие curl-запросы к локальному TLS-серверу; проверки сценариев обрыва/повтора/Range/ошибок; нативные C-движки на малых объёмах; fault injection только в тестовых сборках; сохранение пользовательского контрольного файла; manifest/bootstrap с подставным файловым транспортом. Исходники предназначены для Bash 3.2, но этот интерпретатор и реальная macOS здесь не запускались. Нет измерения сети пользователя, полной нагрузки 48 ГиБ, реального 40-ГиБ bridge, проверки Apple cache controls или Metal execution. Точный результат и команды — в QA_RESULTS.md и qa-linux.log. CI-статус на GitHub необходимо читать отдельно: наличие workflow не означает его успеха.

Логи могут содержать серийные номера и сетевые сведения. Автоматической отправки логов в GitHub нет. Перед публичной публикацией удалите личные идентификаторы. `/tmp` в полной macOS может находиться на SSD; никаких обещаний «вообще ноль записей на SSD» не даётся.

Справочные первоисточники: curl man page (retry/output, Range); Apple man pages mlock(2), fcntl(2). URL приведены в POST_REPAIR_EN.md.
