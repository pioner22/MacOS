# Dimanger: архитектура и требования

Дата: 5 ноября 2026 года. Редакция: проект 0.1. Статус: предложение до реализации.

Документ отделяет проверенные свойства внешних технологий от проектных решений Dimanger. Ссылки вида [S01] раскрыты в [перечне первичных источников](SOURCES.md). Все описания будущих функций являются требованиями, а не отчётом об уже работающем приложении.

## 1. Назначение

Создать управляемый с Mac личный VPN: мастер подключается к Linux-серверу, подготавливает его, устанавливает службу, регистрирует устройство и проверяет передачу трафика. Обычное подключение клиента к этому серверу использует TCP:80 и обходится без TLS, HTTPS и сертификатов X.509 на этом участке.

Dimanger должен иметь собственные сообщения, управление сессиями, транспортные профили, установщик, обновления, диагностику и интерфейс. Для криптографических операций используются известные конструкции и существующие реализации с проверкой интеграции.

Цель противодействия распознаванию формулируется измеримо: оценить конкретный профиль в перечисленных сетях, против перечисленных пассивных классификаторов и активных проверок, с указанием версии и даты. Неизвестность названия протокола не является гарантией доступности.

## 2. Границы задачи

| Область | Решение |
| --- | --- |
| Канал клиента Dimanger до своего сервера | Собственное туннелирование без TLS/X.509 |
| Основа доставки через Интернет | IP и TCP сохраняются |
| Подготовка и управление сервером | SSH с проверкой ключа узла |
| Первичная доставка программы | Проверенный канал и подпись издателя; HTTPS допустим |
| Посещение сайтов через туннель | Их HTTPS остаётся сквозным между приложением пользователя и сайтом |
| Подпись macOS-приложения | Требования Apple выполняются отдельно |
| Веб-страница на сервере | Обычный публичный HTTP без секретов |
| Устойчивость к блокировке IP или отсутствию связности | Не обеспечивается упаковкой трафика |

Буквальный отказ от всех стандартных протоколов несовместим с требованием HTTP/TCP и работой в обычном Интернете. Предлагаемое уточнение цели: собственный VPN-протокол без зависимости от TLS и готового VPN-протокола на участке клиент — сервер.

Оператор туннельного сервера получает доступ к расшифрованным IP-пакетам на выходе. Пользовательский HTTPS внутри них остаётся зашифрованным до сайта. Защита устройства или сервера после их полного взлома не обеспечивается самим туннелем.

## 3. HTTP и порт 80

HTTP определяет синтаксис и поведение сообщений; номер порта не заменяет эти требования [S01].

| Транспорт | Преимущества | Ограничения |
| --- | --- | --- |
| Собственные бинарные сообщения поверх TCP:80 | Управляемое внешнее представление; нет TLS-рукопожатия; соответствует идее нового транспорта | Не является HTTP; может отклоняться сетью, разрешающей только корректный HTTP |
| Корректные HTTP-запросы и ответы с защищённым содержимым | Возможна интеграция с обычной HTTP-инфраструктурой | Заголовки и поведение видимы; поток может классифицироваться как туннель |
| WebSocket без TLS с внутренним шифрованием | Удобная двусторонняя связь; поддерживается nginx | Стандартное распознаваемое рукопожатие; это профиль совместимости |

Базовый кандидат первой версии — собственный бинарный транспорт. HTTP-носитель допускается как отдельная будущая возможность при подтверждённой потребности. Переключение через HTTP Upgrade открыто сообщает о смене протокола; WebSocket не является способом сделать внешний протокол неизвестным [S02, S03].

Случайное заполнение, смена размеров и интервалов могут менять признаки, но сами по себе не доказывают неразличимость. Исследования показывают пассивную классификацию полностью зашифрованных потоков и распознавание некоторых обфусцированных прокси по структуре вложенного обмена [S07, S09]. Это свидетельства о конкретных исследованных системах, а не описание каждого провайдера в 2026 году.

## 4. Состав системы

| Компонент | Ответственность |
| --- | --- |
| Приложение Dimanger для macOS | Мастер, профили, состояние подключения, управление устройствами, диагностика |
| Системное сетевое расширение | Приём IP-пакетов от macOS, передача через защищённый канал, возврат ответных пакетов |
| Общее протокольное ядро | Рукопожатие, проверка ключей, состояния сессии, защищённые сообщения, лимиты |
| Серверная служба dimangerd | TCP:80, авторизация устройств, сайт, туннельные сессии |
| Привилегированный компонент Linux | Только необходимые действия с TUN, маршрутизацией и правилами межсетевого экрана |
| Административная утилита dimangerctl | Статус, устройство, ключи, диагностика, установка и обновление через локальный доступ/SSH |
| Подсистема выпуска | Подписанные версии, манифест совместимости, проверки обновлений |
| Транспортный профиль | Внешнее представление, упаковка и политика задержек в пределах заданного бюджета |

Предпочтительный стек для проверки осуществимости: Rust для общего ядра и Linux-службы, Swift/SwiftUI для приложения и интеграции с macOS. Конкретные библиотеки и версии закрепляются после технической пробы. Snow — возможный кандидат реализации Noise; её README прямо сообщает об отсутствии формального аудита [S14]. Это не основание считать будущий Dimanger проверенным.

Граница Swift/Rust должна иметь небольшой интерфейс: входные и выходные буферы ограниченной длины, явное владение памятью, отмена, ошибки и завершение сессии. Сетевое расширение не запускает произвольные загруженные программы. Отдельная сборка и тесты нужны для Intel и Apple Silicon.

## 5. Один публичный вход для сайта и VPN

Публичный TCP:80 принимает один компонент. Для первой версии предлагается dimangerd со встроенным обработчиком небольшой статической страницы.

Схема связей:

- Обычный браузер → публичный TCP:80 → обработчик HTTP → HTML, CSS и поисковая форма.
- Клиент Dimanger → тот же TCP:80 → ограниченная обработка рукопожатия → авторизованная сессия → TUN → маршрутизация Linux.
- Мастер установки → отдельный административный SSH-доступ → локальные административные команды.

Если нужен nginx, он слушает только локальный адрес или внутренний сокет и получает обычные HTTP-соединения от входного компонента. При таком варианте необходимо сохранять уже прочитанные байты и проверять согласованность обработки HTTP. Обычный HTTP reverse proxy нельзя считать готовым обработчиком произвольного двоичного протокола.

Для WebSocket-профиля возможна другая схема: nginx принимает внешний HTTP и передаёт переключённое соединение локальной службе. Поддержка такого режима документирована nginx [S03]. Одновременное независимое назначение nginx и dimangerd на один адрес и TCP-порт не создаёт требуемого разделения соединений.

Входной компонент обязан ограничивать время чтения, размер буфера до авторизации, число незавершённых соединений и стоимость проверки. Криптографическую ошибку нельзя превращать в подробную публичную диагностическую страницу.

Не следует обещать, что любой неавторизованный двоичный запрос получит настоящий сайт: HTTP-страница предназначена для корректных HTTP-запросов. Поведение на прочие данные и его отличимость исследуются отдельно. Возврат HTML на случайные байты также может стать отличительным признаком.

Распознавание HTTP и туннельного начала должно быть однозначным. Версия формата обязана определить приоритет разборщиков, границы буферов и поведение при совпадении начальных байтов. Нельзя незаметно менять разборщик посередине соединения или полагаться на границы TCP-пакетов.

## 6. Ключи и доверие

Предлагаемый криптографический профиль для прототипа: Noise_IK_25519_ChaChaPoly_SHA256.

Доверие к серверу устанавливается заранее: мастер получает его открытый VPN-ключ через SSH после проверки ключа SSH-узла. Сервер регистрирует открытый VPN-ключ конкретного Mac. Чужой открытый ключ не становится доверенным только потому, что пришёл в первом сетевом ответе.

| Материал | Создание и хранение | Передача |
| --- | --- | --- |
| Закрытый VPN-ключ сервера | На сервере, отдельные права доступа | Не покидает сервер |
| Открытый VPN-ключ сервера | На сервере | Через проверенный SSH в профиль Mac |
| Закрытый VPN-ключ устройства | На Mac, хранилище с ограниченным доступом | Не передаётся установщику на сервер |
| Открытый VPN-ключ устройства | На Mac | Через проверенный SSH в список разрешённых |
| Временные ключи сессии | Каждое соединение отдельно | По правилам выбранной криптографической реализации |
| Ключи проверки выпусков | Корень доверия процесса выпуска | Открытая часть закрепляется в проверенном приложении |

Пара ключей — открытая и закрытая части одной идентичности. Клиенту и серверу нужны свои идентичности. Скачивание серверного закрытого ключа на Mac в штатном сценарии не предусмотрено.

Фраза «ключ 4048 байт» не определяет стойкость. Если имеется в виду RSA-4096, 4096 бит равны 512 байтам размера модуля, а не всего файла. Для X25519 используются 32-байтные значения; оцениваемая стойкость Curve25519 приблизительно 128 бит [S05]. Длину файла ключа нельзя сравнивать со стойкостью шифрования.

Постоянный секрет не передаётся первым пакетом. Владение закрытым ключом подтверждается в криптографическом обмене. Секретный URL, фиксированная строка или адрес сайта не заменяют авторизацию.

На Mac требуется решить доступ к хранилищу ключа из системного расширения, включая состояние до и после разблокировки сеанса. Само использование Keychain не доказывает доступность ключа во всех состояниях и не означает аппаратное хранение произвольного X25519-ключа. До подтверждения матрицы состояний автоматическое подключение до входа пользователя не обещается.

## 7. Установление и завершение сессии

Предлагаемый порядок:

1. Mac открывает TCP-соединение.
2. Транспорт выделяет ограниченное сообщение рукопожатия.
3. Клиент выполняет начало Noise IK с закреплённым серверным ключом.
4. Сервер проверяет сообщение и разрешение ключа устройства.
5. Сервер отправляет свой ответ.
6. Клиент завершает криптографический обмен и отправляет защищённое подтверждение канала.
7. Сервер проверяет подтверждение, выдаёт параметры туннеля и разрешает пересылку IP-пакетов.
8. Клиент применяет параметры маршрутизации/DNS и выполняет проверку передачи.
9. Только после её успеха интерфейс показывает «Подключено».

Noise IK выбран как кандидат с заранее известным ключом сервера. Его первый пакет нельзя считать окончательным доказательством живой авторизованной сессии: ранние данные допускают повтор, а свойства ответного трафика усиливаются после сообщения клиента [S04]. Поэтому в проекте запрещены ранний пользовательский трафик, выдача настроек и административные действия до подтверждения канала.

При неверном ключе сервера соединение завершается. Автоматический переход на неподтверждённый новый ключ, отключение шифрования или другой более слабый профиль запрещён. Совместимость версий проверяется по аутентифицированным данным.

Состояния ядра: подключение, рукопожатие, ожидание подтверждения, настройка, работа, завершение, ошибка. Состояния интерфейса отдельно отражают готовность сетевых настроек и фактический тест доступа: поднятый сокет не равен работающему VPN.

После разрыва выполняется новое рукопожатие. Состояние шифрования завершённой сессии не восстанавливается из случайно сохранённых счётчиков. Перезапуск службы не должен оживлять старую авторизацию.

Штатное завершение подтверждается аутентифицированным сообщением. EOF или разрыв до него считается аварийным завершением. Неполная запись не доставляется в TUN; ранее проверенные и доставленные IP-пакеты не отменяются. AEAD не позволяет определить, был ли обрыв после полных записей вызван сетью или намеренным действием посредника.

## 8. Защищённые сообщения и обфускация

Собственная часть Dimanger описывает виды сообщений: параметры сеанса, подтверждение, IP-пакет, проверка жизнеспособности, завершение и служебная ошибка внутри уже защищённого канала.

Требования к формату:

- Ограничить длину записи до выделения памяти.
- Хранить полезную длину, тип и значимые управляющие поля внутри аутентифицированного сообщения.
- Использовать отдельное криптографическое состояние для каждого направления.
- Выполнять управление счётчиками через выбранную библиотеку.
- Не допускать повторного сочетания ключа и nonce; это требование AEAD [S06].
- Привязать версию и профиль к аутентифицированному обмену.
- При ошибке подлинности завершить сессию и ничего не передавать в TUN.
- Ограничить очереди, обратное давление и общий объём незавершённых сообщений.
- Не включать сжатие секретов и данных недоверенного происхождения в первой версии.

Для лабораторного прототипа допустима простая внешняя длина записи. Полный побайтовый формат, пределы и тестовые векторы фиксируются на этапе протокольной спецификации. Не следует выдавать такой прототип за завершённую маскировку.

Шифрование внутренней длины не скрывает видимый объём TCP-трафика. Noise сам по себе также не скрывает все признаки рукопожатия [S04]. Дополнительное внешнее кодирование, заполнение и планирование отправки требуют отдельной модели и проверки.

Первый исследовательский профиль должен:

- Иметь формальное описание кодирования и декодирования.
- Обрабатывать всё начало соединения, а не только пользовательские данные после него.
- Не публиковать постоянный маркер Dimanger как необходимую часть распознавания.
- Учитывать отличимость временных открытых ключей и размеров сообщений.
- Иметь ограниченный, измеримый расход трафика и задержку.
- Сохранять криптографические свойства ядра.
- Не позволять неаутентифицированному удалённому узлу выбирать произвольный режим или загружать код.
- Иметь версию и проверенные границы совместимости.

Замена транспортного оформления не должна требовать переписывать авторизацию, ключи и шифрование. Но каждая новая композиция всё равно проходит анализ: модульность не является доказательством безопасности.

## 9. Повторы, активные проверки и ограничения ресурсов

Проект различает два свойства:

1. Повтор записанного пакета не получает доступ к VPN.
2. Повтор записанного пакета не помогает определить тип сервера.

Второе свойство существенно сложнее первого. Исследования обнаруживали отличия даже у служб, которые молчат без секрета [S08]. Поэтому сайт, молчание и кэш повторов не объявляются универсальной защитой.

Для прототипа предусматриваются ограничение незавершённых подключений, лимит памяти и времени, ограниченный кэш повторных первых сообщений, журнал агрегированных ошибок без ключей и содержимого. Тесты включают состояние после перезапуска, истечение кэша, одновременные повторы, частичные сообщения и медленную передачу.

Транспортный профиль не защищает от перегрузки внешнего канала. Защита от полного отказа сети, блокировки адреса сервера и компрометации хоста находится за границами обещаний.

## 10. IP-туннель и производительность

Первый функциональный вариант должен быть настоящим IP-туннелем:

- На macOS пакеты получает сетевое расширение.
- На Linux служба работает с TUN.
- Для каждого разрешённого устройства определяется допустимый адрес/подсеть.
- Сервер запрещает подмену внутреннего адреса и неаутентифицированный транзит.
- Выход в Интернет обеспечивается маршрутизацией и при необходимости NAT.
- Обратные пакеты направляются соответствующей сессии.
- Клиентская маршрутизация сохраняет доступ к адресу самого туннельного сервера вне туннеля.
- MTU выбирается и проверяется для обоих семейств IP; сообщения о слишком большом пакете и превышение лимита обрабатываются явно. Размер записи туннеля не приравнивается к размеру TCP-сегмента.

Наличие SOCKS-прокси или успешного эхо-ответа не считается готовым VPN.

Передача внутренних TCP-соединений через внешний TCP может ухудшать задержки и скорость при потерях. Внешняя доставка по порядку задерживает последующие данные, включая UDP приложений [S10]. Нельзя обещать низкую задержку звонков и игр до измерений.

Матрица испытаний включает различные RTT, потери, несколько одновременных потоков, большой и маленький размер передачи, смену Wi-Fi, сон и пробуждение. Несколько внешних TCP-соединений могут сократить взаимное влияние потоков, но не отменяют фундаментальные свойства TCP.

UDP-транспорт возможен отдельным поздним этапом. Он потребует собственной спецификации доставки, управления перегрузкой, защиты от повторов и усиления трафика. Он не входит в подтверждённую первую версию.

## 11. DNS, IPv6 и защита от прямого выхода

До изменения маршрутов клиент сохраняет исходное сетевое состояние. Нормальное отключение восстанавливает только принадлежащие ему настройки.

DNS-резолвер задаётся профилем, а запросы следуют выбранному режиму туннеля. IPv6 либо поддерживается полностью, либо ограничивается в соответствии с профилем, чтобы не обходить IPv4-туннель. Решение нельзя считать принятым без проверки на реальной macOS и сервере.

Предусматриваются два явных режима:

- Обычное отключение: туннель завершается, прямой доступ возвращается.
- Режим блокировки прямого выхода: разрыв или авария туннеля оставляет пользовательский доступ заблокированным до переподключения либо явного отключения блокировки.

Название кнопки и интерфейс обязаны показывать, какой режим действует. Обновление, переустановка и временная ошибка не должны без уведомления менять выбранную политику.

Полная гарантия отсутствия любого системного пакета вне туннеля не заявляется. Для каждой поддерживаемой версии macOS документируются необходимые системные исключения, поведение сетевого расширения при аварии и фактически проверенный охват защиты. Выход за эти ограничения должен давать понятный статус.

Проверка включает DNS, IPv4/IPv6, смену интерфейса, падение процесса, перезапуск расширения и обновление. Тест через один сайт с показом IP недостаточен.

## 12. macOS: приложение, подписи и разрешения

Целевая поставка: приложение Dimanger, системное расширение с NEPacketTunnelProvider, команда управления и диагностический отчёт. Apple документирует этот API для собственного пакетного VPN [S11].

Для прямой поставки с сайта/репозитория используем вариант системного расширения с Developer ID и соответствующим разрешением Network Extension. Согласно таблице Apple, macOS-вариант packet tunnel в виде app extension ограничен App Store, а system extension допускает прямое распространение [S12]. Требования подписи и активации проверяются отдельно [S13].

Пользователь проходит штатные системные запросы разрешений. Установщик не отключает SIP, Gatekeeper, проверку TLS у системных инструментов или защиту macOS.

Подпись Apple подтверждает происхождение программы; TLS-сертификат защищает конкретное сетевое соединение. Отказ от второго в собственном туннеле не отменяет первого при выбранном способе поставки.

Предварительная матрица: Intel и Apple Silicon; конкретный минимум macOS определяется технической пробой и доступным набором сборки. Совместимость с Big Sur, текущими версиями, входом пользователя и автозапуском должна быть проверена до обещания поддержки.

Без готовой подписанной поставки возможен лабораторный клиент для разработки. Он не считается полноценной пользовательской заменой приложения и не распространяется как готовое решение с отключением системных проверок.

## 13. Мастер установки на Mac

### Шаг 1. Проверка локальной среды

Определить архитектуру и версию macOS, наличие необходимых разрешений, установленную версию Dimanger, занятые сетевые профили и конфликтующий VPN. Показать условия поддержки. Сборочные инструменты не требуются конечному пользователю.

### Шаг 2. Подключение к серверу

Запросить адрес, SSH-порт, имя пользователя и способ входа: SSH-ключ/агент либо пароль. При наличии — поддержка сертификата SSH как административной учётной записи. Это не TLS-сертификат туннеля.

Пароль вводится локально, не попадает в командную строку, shell history, файл диагностики или HTTP. Проверка ключа SSH-узла обязательна; при первом контакте мастер показывает отпечаток для проверки по независимому каналу. Изменившийся известный ключ останавливает автоматический сценарий.

### Шаг 3. Предварительная проверка сервера

Проверить дистрибутив, архитектуру, права, свободное место, TUN, маршрутизацию, порт 80, действующие сайты, настройки межсетевого экрана и способ административного восстановления. Базовая цель прототипа — Ubuntu 24.04 LTS; остальные системы добавляются после тестирования.

Если порт занят, мастер предлагает конкретный совместимый план. Он не останавливает существующий веб-сервер автоматически и не заменяет чужие правила сети.

### Шаг 4. План изменений

Показать будущие пакеты, файлы, службы, сетевые правила, ожидаемое влияние и точки отката. Выбор «Развернуть» запускает этот конкретный план. Отдельно указываются возможный перезапуск служб и необходимость перезагрузки системы.

### Шаг 5. Обновление пакетов

Обновить индекс пакетов и выполнить выбранный режим обновления. Для нового выделенного сервера можно предложить обновление установленных пакетов; для используемого — показать список и влияние. Не выполнять смену основного выпуска ОС или автоматическую перезагрузку как скрытую часть установки VPN.

Мастер показывает текущий этап, реально полученные события, обработанные пакеты и журнал без секретов. Если точный процент неизвестен, используется индикатор выполнения без вымышленного процента.

### Шаг 6. Установка выпуска Dimanger

Скачать конкретную версию, проверить подписанные метаданные и хеш, распаковать в отдельный каталог версии, проверить конфигурацию и зависимости. При отсутствии доступа сервера к репозиторию мастер может передать уже проверенный пакет через SSH.

Первый доверенный установщик не загружается с неаутентифицированной HTTP-страницы с автоматическим исполнением. Подпись, ключ которой получен из того же непроверенного источника, не решает проблему первого доверия.

### Шаг 7. Служба и сайт

Создать системную учётную запись, каталоги и права, ограниченный служебный модуль, TUN, именованные правила маршрутизации и межсетевого экрана. Сохранить необходимые данные для отката, проверить конфигурацию и доступность SSH. Добавить службу в автозапуск только после успешной проверки её настроек.

Для сайта установить локальные статические ресурсы и поисковую форму. nginx устанавливать только при необходимости выбранной схемы.

### Шаг 8. Регистрация устройства

Создать ключ сервера, если он ещё не существует. Создать ключ Mac локально. Передать открытые части через проверенный административный канал. Создать профиль с адресом, закреплённым серверным ключом, версией протокола и сетевой политикой.

Повторный запуск мастера не должен без причины менять идентичность сервера и отзывать ранее зарегистрированные устройства.

### Шаг 9. Подключение и проверка

Проверить доступ к TCP:80, рукопожатие, ключ сервера, разрешение клиента, обмен защищённым сообщением, TUN, маршруты, DNS и реальный выход трафика. По отдельности отобразить результат каждого слоя.

Внешняя проверка IP и доступности использует явно указанный сервис или контролируемый тестовый узел. Не передавать в сторонний сервис ключи, профиль или журнал. Для полноценного доказательства маршрутизации использовать также наблюдение на клиенте и сервере.

### Шаг 10. Завершение

Показать адрес, версии клиента и сервера, отпечаток идентичности, статус VPN, режим прямого доступа и результат проверок. Сохранить отчёт без закрытых ключей и административных паролей. Выход с ошибкой не отображается как успешная установка.

Отмена в критическом этапе переводит мастер в безопасную точку остановки или выполняет предусмотренный откат. Повторный запуск продолжает установку по состоянию, не дублируя правила и службы.

## 14. Управление после установки

| Действие | Ожидаемое поведение |
| --- | --- |
| Включить | Проверить профиль, установить канал, применить настройки, проверить передачу |
| Выключить | Завершить сеанс, выполнить явно выбранную политику прямого доступа |
| Статус | Версии, состояние, доступность, время сессии, счётчики, последняя ошибка |
| Проверить | Последовательно проверить сервер, авторизацию, сеть, DNS, IPv6 и выход |
| Обновить | Проверить выпуск, совместимость и подпись; выполнить транзакционную замену |
| Переустановить | Восстановить файлы программы с сохранением ключей и профилей по умолчанию |
| Пересоздать ключи | Отдельная операция с показом последствий и повторной регистрацией |
| Отозвать устройство | Запретить новые сессии и завершить активные сессии этого ключа |
| Удалить | Удалить принадлежащие проекту компоненты; отдельно выбрать сохранение данных |
| Отчёт | Собрать обезличенную техническую диагностику с предварительным просмотром |

Предполагаемые команды после реализации: dimanger on, off, status, doctor, update и reinstall. Сейчас эти команды не выпущены.

Обновление подписки существующего BigSurVPN не является обновлением Dimanger. Общая кнопка мастера должна различать версию клиента, версию серверной службы и профиль соединения.

## 15. Подписанные обновления и откат

Хеш подтверждает соответствие файлу, но его происхождение должно подтверждаться доверенной подписью. Процесс выпуска отделяется от ключей VPN-сервера.

Выбранная схема обновлений должна защищать от подмены, навязанного старого выпуска, несовместимого сочетания клиента и сервера, а также от незаметного удержания устаревших метаданных. Для выбора реализации используется модель TUF [S15]; одна подпись ZIP не означает реализацию всего TUF.

Порядок: загрузка новой версии → проверка метаданных → проверка конфигурации → резервирование текущей версии → переключение → проверка здоровья → фиксация или откат.

Данные мигрируются так, чтобы объявленный откат оставался возможным. Откат к локальной ранее проверенной версии после неудачной установки и навязанное сетевым посредником понижение — разные операции. Политика должна различать их.

Обновление приложения и расширения выполняет требования Apple. Автозагрузка неизвестного исполняемого модуля маскировки не допускается. Новые профили распространяются в проверенном выпуске.

## 16. Страница поиска

Первая версия — настоящая простая страница с собственной нейтральной стилистикой, строкой поиска и отправкой запроса выбранному внешнему поисковику. Это не собственный поисковый индекс.

У страницы нет формы входа администратора, выдачи приватных ключей, управления VPN или непроверенной команды установки. Её публичная работоспособность не подтверждает нераспознаваемость туннеля.

Переход к поисковику по HTTPS допустим. Начальная страница по HTTP может быть изменена посредником; поэтому она не участвует в доверии к установщику и ключам.

## 17. Решения, которые завершаются до выпуска

| Вопрос | Предварительное решение | Чем подтвердить |
| --- | --- | --- |
| Обязателен настоящий HTTP или только TCP:80 | Базовый вариант — TCP:80 | Явная фиксация требований до стабилизации протокола |
| Криптографическая реализация | Существующая библиотека Noise | Векторы, анализ интеграции и зависимостей |
| Побайтовый формат | Небольшой ограниченный формат записей | Спецификация, отрицательные тесты, совместимость |
| Конкретная обфускация | Исследовательский отдельный этап | Классификаторы, активные проверки, задержка и накладные расходы |
| Минимальная macOS | Определяется технической пробой | Подписанная сборка и реальная установка на обеих архитектурах |
| Блокировка прямого выхода | Явная политика с описанными исключениями | Падение, смена сети, DNS/IPv6, обновление |

План реализации и проверяемые результаты каждого этапа находятся в отдельном документе. До их выполнения Dimanger не имеет подтверждённых показателей скорости, незаметности, стабильности или готовности к эксплуатации.
